# 0002. Своя авторизация с путём на Ory

- Дата: 2026-09-17
- Статус: принят

## Контекст

identity появляется уже в вехе 0: регистрация, вход по паролю, сессии. В вехе 3 добавляются проверка сессии на gateway, внутренние токены, вход через GitHub, подтверждение email и сброс пароля. До первой строки кода нужно решить, пишем это сами или берём готовое.

Ограничения:

- Главная цель проекта — учебная. Пароли, сессии, OAuth2 и CSRF есть в карте знаний вех 0 и 3.
- Рынок — весь мир, минимум GDPR обязателен, персональные данные хранит только identity (#1). Может понадобиться хранить данные россиян в РФ.
- Если проект станет сервисом, организациям понадобятся SSO и MFA. Поддерживать их в одиночку дорого.

## Варианты

- **Своя авторизация в identity.** Механику паролей, сессий и OAuth2 разбираешь изнутри. Данные и контракт полностью наши, в compose одним сервисом меньше. Минус: все дыры наши, а MFA, passkeys и SSO придётся писать и поддерживать самим.
- **Ory Kratos у себя (и Hydra, если нужен свой OAuth2-сервер).** Проверенные сценарии регистрации, восстановления доступа, MFA и passkeys, меньше своего кода в зоне риска. Минусы: изучаешь конфиг Kratos, а не механику. Добавляется ещё один сервис со своей базой и миграциями. Интерфейс входа всё равно свой. Внутренние токены и JWKS для сервисов всё равно писать самим.
- **Ory Network (облако).** Ничего не надо эксплуатировать. Минусы: для учёбы те же, что у Kratos. Персональные данные лежат в чужом облаке, а это не сходится с #1. Появляется зависимость от тарифа.

## Решение

Авторизацию пишем сами в identity. Ory Kratos — эталон: форматы данных и границы выбираем так, чтобы переезд на self-hosted Kratos затронул только identity. Отступаем от совместимости с Ory, только если другое решение явно лучше, и записываем почему.

### Как держим путь на Ory

1. **Граница — контракт `identity.v1`.** Gateway и сервисы знают только его и внутренний токен. Понятия Kratos (flows, его cookie сессии) в контракт не попадают. После переезда identity станет прослойкой над Kratos и продолжит выдавать внутренние токены.
2. **`user_id` наш.** Сервисы не видят id из Kratos, соответствие хранит identity.
3. **Пароли — PHC-строка argon2id** (#187). Kratos импортирует такие хэши, сбрасывать пароли при переезде не придётся.
4. **Данные пользователя ложатся на модель Kratos.** Email и ник — traits, подтверждённый email — verifiable address, вход через GitHub — пара provider и subject из `oauth_accounts`.
5. **Только стандартные протоколы:** OAuth2 authorization code с PKCE, OIDC, TOTP по RFC 6238, passkeys через WebAuthn. Самодельные схемы при переезде не переносятся.
6. **Роли и права — не часть Kratos.** Они остаются у нас, дальше по плану OpenFGA.
7. **Отступление от Ory** описываем в PR: почему решение явно лучше и что сломается при переезде.

Сессии при переезде не переносим: все пользователи один раз войдут заново. Страницы входа в web перепишем под flows Kratos. Это фронтенд, цена приемлемая.

## Последствия

Проще:

- Учебная часть вех 0 и 3 остаётся.
- Персональные данные лежат в одной базе, которую мы контролируем. Это решение #1.
- Когда понадобятся SSO или MFA, переезд на Kratos не затронет другие сервисы.

Сложнее и рискованнее:

- Дыры наши: перебор паролей, раскрытие существующего email (#58), фиксация сессии (#59), токены сброса (#64), атаки на OAuth (#63). Защита:
  - криптографию не пишем сами: `golang.org/x/crypto/argon2`, `golang.org/x/oauth2`, `go-oidc` для OIDC-провайдеров, проверенная библиотека для JWT;
  - сверяемся с OWASP ASVS и OWASP Cheat Sheets;
  - в демо вехи 3 входит аудит OWASP.
- Каждое новое поле или сценарий в identity проверяем на совместимость с Kratos.

Пересмотреть и переехать на self-hosted Kratos, если:

- организациям нужен корпоративный SSO (SAML, OIDC) или обязательный MFA;
- появились живые пользователи, а поддержка входа отнимает время у других вех;
- аудит нашёл то, что дешевле заменить, чем чинить.

Ory Network не рассматриваем, пока персональные данные должны оставаться у нас.
