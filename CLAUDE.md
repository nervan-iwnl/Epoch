# Epoch — контекст для Claude

Пет-проект: платформа для алгоритмов, контестов, заданий в формате ШАД, курсов с git-домашками, CTF и ML. Архитектура — микросервисы в монорепе с первого дня. **Главная цель автора — учебная:** глубоко разобраться во всём программистском, кроме фронтенда (Linux и песочницы, базы, распределённые системы, безопасность, Kubernetes, SRE). Вторая цель — в теории вырасти в сервис.

## Где что

- `docs/vision.md` — цели, правила проекта, что изменилось относительно первого плана.
- `docs/roadmap.md` — 11 вех, демо и сроки. **Источник правды по плану** — этот файл и issues, а не первый документ CodeSpirit.
- `docs/learning-map.md` — какая веха что прокачивает и что читать.
- `docs/architecture/` — каталог сервисов, схемы, правила межсервисного взаимодействия. Перед работой над сервисом читать `README.md` и профильный документ.
- `docs/adr/` — решения; `docs/journal/` — заметки автора.
- Задачи: https://github.com/nervan-iwnl/Epoch/issues, вехи = milestones «0. Фундамент» … «10. Сервис: организации и масштаб».
- Доска: https://github.com/users/nervan-iwnl/projects/4 (колонки Бэклог → На неделю → В работе → Готово).

## Как помогать — важно

- **Бэкенд, Go, Rust, Linux, базы, инфраструктура: код пишет автор.** Claude объясняет концепции, даёт подсказки по уровням (направление → подход → конкретное место), ревьюит, указывает, что почитать. Готовую реализацию — только если автор прямо попросил («напиши», «сделай сам»).
- **Фронтенд (`web/`) Claude пишет целиком** — автор его учить не хочет.
- Рутина вне учебной цели (CI-обвязка, доки, скрипты для доски) — можно делать самому, если попросили.
- Перед задачей: `gh issue view N`, профильная схема в `docs/architecture/`, связанный ADR.
- Не предлагать откатиться к монолиту и не спорить с принятыми решениями из `docs/vision.md` — это выбор автора.
- **Стиль:** по-русски, коротко и прямо, без корпоративной воды и канцелярита.

## Правила архитектуры (кратко)

Полностью — в `docs/architecture/README.md`.

1. Своя база у каждого сервиса; чужие данные — только через API или события.
2. Контракты API и событий — только в `proto/` (`epoch.<сервис>.v1`), `buf breaking` в CI.
3. В `pkg/` — только платформенный код, без доменной логики.
4. Синхронный вызов — всегда с дедлайном; ретраи только идемпотентных, с jitter.
5. Изменение и событие — в одной транзакции через outbox; консьюмеры идемпотентны.
6. Команды на проверку — NATS JetStream; факты — Kafka.
7. Личность пользователя — только из подписанного внутреннего токена identity, не из заголовков.
8. Новый сервис — только через шаблон (`task new-service`).
